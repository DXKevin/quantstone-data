# QuantStone Data：项目架构、设计原则与开发约定

本文档用于向后续开发者和 Agent 说明 QuantStone Data 的项目定位、已经确定的架构原则、当前实现状态及尚未确定的事项。

阅读时请特别区分：

- **已确定原则**：后续实现应遵守，除非用户明确改变决定。
- **当前实现**：代码库中已经存在并通过测试的功能。
- **规划方向**：可以指导设计，但不代表已经实现。
- **待定事项**：不要擅自固化，应在实现前与用户确认或保持可扩展。

## 1. 项目定位

项目名称：`quantstone-data`  
产品名称：**QuantStone Data**

QuantStone Data 是一套面向个人量化研究的数据基础设施，用于：

- 注册和描述金融数据集；
- 从不同供应商采集数据；
- 对采集结果进行字段对齐和质量校验；
- 管理数据文件、覆盖范围、修订和版本；
- 通过 API 和 SDK 提供稳定的数据发现与读取能力。

QuantStone 可以作为未来一组量化基础设施项目的总品牌。回测系统、因子系统和实盘系统可以成为独立的上层项目，不应直接塞入 `quantstone-data`。

## 2. 最重要的架构结论

### 2.1 统一管理，不强制统一业务结构

本项目遵循：

> 统一管理数据集，但不强制统一不同供应商的数据业务结构。

数据集契约要求单个数据集的字段和语义明确、稳定、可追踪，但不要求不同供应商的数据集具有相同字段。

例如可以同时存在：

```text
tushare.cn.stock.daily
tushare.cn.stock.stk_limit
tushare.cn.stock.stock_basic
ths.cn.stock.daily
```

其中，同花顺日线可以直接包含 ST、涨跌停价等字段；TuShare 可以将这些内容放在不同接口、不同数据集中。本项目不强行将它们合并成一个统一日线表。

### 2.2 供应商接口可以直接决定数据集边界

对于具有明确 API 的供应商，通常采用“一项供应商接口对应一个数据集”的方式。

对于没有标准 API、通过文件交付的数据产品，按照供应商实际提供的数据产品和文件语义划分数据集。

数据集 ID 可以使用供应商 API 名称；频率、接口参数和更新周期等内容作为元数据保存，不必全部重复写入 ID。

### 2.3 统一结构由上层项目按需建立

跨供应商组合和转换不属于数据库层的强制职责。例如回测项目可以自行定义：

```text
tushare.daily
+ tushare.stk_limit
+ tushare.st_status
        ↓
BacktestDailyBar
```

同花顺日线则可能直接转换为 `BacktestDailyBar`。

如果多个上层项目反复使用同一种转换，可将转换器提取为共享库；现阶段不应提前在数据层维护大规模统一金融数据模型。

### 2.4 允许最低限度的技术标准化

不统一业务字段，不代表完全原样保存接口响应。为了可靠存储，可以进行必要的技术处理，例如：

- 将日期字符串转换为 `date`；
- 将时间转换为明确的时间类型；
- 统一字符编码；
- 明确空值表示；
- 转换为 Parquet 支持的数据类型；
- 保证数值精度；
- 记录供应商原字段名和存储字段名。

不得在没有数据集契约说明的情况下，擅自改变字段业务含义或暗中拼接其他数据集。

## 3. 项目职责边界

### 3.1 QuantStone Data 负责

- 数据集注册和 Schema 管理；
- 供应商与数据集元数据管理；
- 首次采集、增量更新和指定范围修复；
- 原始结果进入临时区；
- 字段类型转换和技术标准化；
- 数据契约与质量校验；
- 文件写入、覆盖范围、版本和修订管理；
- 数据目录、运行记录、错误和隔离数据管理；
- 通用 API/SDK：发现数据集、查看 Schema、查看覆盖、读取数据。

### 3.2 QuantStone Data 暂不负责

- 强制统一不同供应商的业务字段；
- 自动构建跨供应商统一日线；
- 为研究生成大量宽表；
- 因子计算；
- 回测引擎；
- 实盘交易；
- 针对某个上层系统的专用业务数据结构。

## 4. 数据集 ID 规则

固定格式：

```text
<provider>.<region>.<instrument>.<dataset>[.<market>]
```

含义：

- `provider`：实际供应商或数据产品的稳定代号；
- `region`：数据区域，例如 `cn`、`hk`；
- `instrument`：品种，例如 `stock`、`etf`、`futures`、`option`；
- `dataset`：供应商 API 名称或供应商定义的数据集名称；
- `market`：可选，仅在不同市场必须使用不同契约时添加。

规则：

- 全部使用小写 ASCII；
- `.` 表示分类层级；
- 同一层级的复合名称使用 `_`；
- ID 一经创建原则上不修改；
- 已启用契约发生实质变化时创建独立的新数据集，不覆盖原数据集；新 ID 优先使用语义名称，必要时使用 `_v2` 后缀；
- 市场不是固定必填层级，只有需要时才追加。

示例：

```text
tushare.cn.stock.daily
tushare.cn.stock.stk_limit
ths.cn.stock.daily
tb_l2.cn.stock.l2_order.sh
tb_l2.cn.stock.l2_order.sz
tb_l2.cn.stock.l2_trade.sh
tb_l2.cn.stock.l2_trade.sz
```

详细规则见 [数据集 ID 命名规范](dataset-id.md)。

## 5. L2 数据的特殊约定

当前讨论中的 L2 数据：

- 通过淘宝购买；
- 通过百度网盘下载和更新；
- 上海与深圳字段或语义不同；
- 分为逐笔委托和逐笔成交。

约定：

- 淘宝是购买渠道，不是供应商身份；
- 百度网盘是交付方式，不是供应商身份；
- `provider` 应代表具体卖家或具体数据产品的稳定代号；
- 上海、深圳需要不同数据契约，因此拆分数据集；
- 逐笔委托使用 `l2_order`；
- 逐笔成交使用 `l2_trade`，不使用含义不够清晰的 `tran`；
- 上海使用 `sh`，深圳使用 `sz`；
- 供应商文件以基本类型交付时，逐笔时间按整数类型声明（例如 `HHMMSSmmm`、自零点起的
  毫秒/微秒计数），并在字段说明和单位中写明编码，不为了统一转换成 `timestamp`；
  `trade_date` 仍使用 `date`，以支持交易日历、逻辑分区和覆盖计算。

深市 Wind L2 已完成首个实测契约：

```text
wind.cn.stock.l2_order.sz
wind.cn.stock.l2_trade.sz
```

源文件为 `SZ/YYYYMMDD/order.parquet` 和 `SZ/YYYYMMDD/trade.parquet`。`symbol` 和
`exchange_code` 都按字符串保存；`channel_code`（源字段“委托编号”）和 trade 的
`order_code`（源字段“委托代码”）原始规范都是 `char(1)`，必须按字符串保存。`event_time`
为 `HHMMSSmmm` 整数；价格保存为放大 10,000 倍的整数。`l2_order` 主键为
`trade_date + symbol + exchange_order_no`，`l2_trade` 主键为
`trade_date + symbol + trade_no`，两者都按交易日做日分区发布。`channel_code` 只作为
普通字段保留，不进入主键；按实际数据约定，交易所委托号在同一证券同一交易日内唯一。深市两个数据集每日约
1.24 GB / 1.70 GB，分别约 1.16 亿 / 1.04 亿行。沪市字段值域不同且当前样本只有 order
文件，需单独建立契约。

原始 Wind 规范还说明：`l2_order.order_type` 深市为 `0=限价、1=市价、U=本方最优`，
与 `side` 组合为 `0B/0S/1B/1S/UB/US`；沪市则使用 `A=正常委托、D=撤单`。
`l2_trade.trade_code` 深市 `C` 表示撤单，空表示成交；9:15 前成交价格为 0。合并后的
Parquet 会出现 `0.0` 浮点、`0` 字符串等类型漂移，后续重写迁移必须按原始 `char(1)`
规范恢复为字符串，不能把合并文件的推断类型当作契约。

中泰证券历史 L2 深市数据也建立了独立契约：

```text
zhongtai.cn.stock.l2_order.sz
zhongtai.cn.stock.l2_trade.sz
```

它们与 Wind 深市 L2 使用完全相同的字段名、类型和主键，转换时做值映射：
`SecurityID -> symbol/exchange_code`、`TransactTime/tradetime -> event_time`、
`ChannelNo -> channel_code`、`ApplSeqNum -> exchange_order_no/trade_no`、
`OrderType` 的 `2/1/U -> 0/1/U`、`Side` 的 `1/2 -> B/S`、`Price*10000 -> int64`、
`ExecType` 的 `F/4 -> 0(成交)/C(撤单)`。中泰 trade 没有 BS 标志，但可以用委托时间
和序号还原：按 `ChannelNo + SecurityID + ApplSeqNum` 关联买卖委托，成交中较晚到达的
委托方是主动方；同一毫秒内序号较大者较晚。用 Wind 的 `side` 对照验证，6,987 万笔成交
100% 一致；中泰该字段可还原，撤单记录为空。`Side 1/2` 的映射同时用委托价与成交价
复核。中泰数据设置为 `manual` 更新频率并标记历史数据集，仅作为历史补齐。

最终形成四个数据集：

```text
<provider>.cn.stock.l2_order.sh
<provider>.cn.stock.l2_order.sz
<provider>.cn.stock.l2_trade.sh
<provider>.cn.stock.l2_trade.sz
```

## 6. 数据集契约

每个注册数据集至少应描述：

- 数据集 ID；
- 显示名称和说明；
- 更新频率（日更、周更、月更或手动）；
- 最小时间颗粒（逐笔、3 秒、秒、分钟、小时、日或无）；
- 是否历史数据集（历史数据集不参与覆盖热力图和日更跟踪）；
- 供应商；
- 区域；
- 品种；
- 数据集/API 名称；
- 可选市场；
- Schema 版本；
- 字段名称、类型、含义、单位、供应商原字段名；
- 是否允许为空；
- 主键或唯一键；
- 时间字段；
- 数据粒度；
- 采集参数和时间范围能力；
- 逻辑分区规则；
- 物理文件组织策略；
- 更新和修订策略；
- 完整性与质量规则；
- 供应商接口或产品版本。

当前实现只覆盖其中的核心身份信息、Schema、字段、主键和时间字段。采集、分区、存储和质量策略将在后续模块中增加。

### 6.1 字段类型

字段契约的 `data_type` 是封闭枚举，当前只开放 Parquet 原生支持且语义明确的类型：

- `string` → Parquet BYTE_ARRAY / UTF8；
- `int32`、`int64` → INT32 / INT64；
- `float32`、`float64` → FLOAT / DOUBLE；
- `boolean` → BOOLEAN；
- `date` → DATE（Arrow `date32`，只到天，无时间）；
- `timestamp` → TIMESTAMP(MICROS)，表示无时区的交易所本地时间，例如
  `2026-11-19 09:30:00`；带时区的值会被拒绝，不做静默换算。

Registry 在创建和修改数据集时校验枚举，未知类型直接返回 422。采集器统一调用
`field_types.normalize_value` 把供应商源值转换为契约类型，并由 `field_types.arrow_type`
生成 Parquet Schema，不再各自维护一份类型映射。`date` 当前接受 `YYYYMMDD` 字符串、
`datetime.date` 或 `datetime`，空值保持为空；`timestamp` 接受无时区的 `datetime` 或
ISO 8601 字符串（日期与时间用空格或 `T` 分隔），带时区偏移的值直接拒绝。供应商原生以
整数编码的时间（例如 L2 逐笔时间）保留为 `int32` / `int64`，不强制转换成 `timestamp`；
只有确实表示“日期 + 时间”的字段才使用 `timestamp`。

暂不开放的常见类型：

- `decimal`：Parquet 支持 DECIMAL，但契约还需要精度和小数位定义；当前价格字段使用
  `float64`；
- 嵌套 `struct`、`list`、`map`：Parquet 支持，但当前字段编辑、预览和校验都按单列模型
  设计，暂不开放。

新增类型时必须同时修改共享类型模块、前端字段下拉、测试和本文档，不能只在单个采集器里
增加映射。

## 7. Registry 与 Catalog

这两个概念必须分开：

### 7.1 Dataset Registry

Registry 描述“数据应该是什么”：

- 数据集定义；
- Schema 版本；
- 字段契约；
- 主键和时间字段；
- 采集、存储和校验策略。

Registry 是运行时数据集契约与状态的权威来源。项目同时可以在代码中维护少量经过验证的
“预置契约”，用于把常用契约作为项目资产进行版本管理，并帮助用户快速创建 Registry 草稿。
预置契约只提供创建时的初始值：它不会在服务启动时自动创建数据集，也不会同步或覆盖已经
存在的 Registry 记录。预置契约的变化必须经过代码评审和测试；草稿可直接编辑，已启用数据集
的实质契约变化通过创建独立的新数据集处理。新旧数据集不建立版本、替代或父子关系。

### 7.2 数据集大类

数据集大类是用户维护的目录组织信息，例如“A股数据”“期货数据”。一个数据集最多归入一个
大类，也可以保持未分类。大类不参与数据集 ID、Schema、采集绑定、审核、存储路径或 Catalog
计算；更改大类不会产生契约版本。为避免误操作，仍包含数据集的大类不能删除，必须先将其下
数据集移出或改归其他大类。

### 7.2 Data Catalog

Catalog 描述“实际上已经有什么”：

- 已发布的逻辑分区；
- 日期覆盖范围和缺口；
- 对应物理文件；
- 行数、大小、校验和；
- 数据版本和修订；
- 采集任务和发布时间；
- 数据质量结果。

增量更新不能简单使用“最大日期加一天”，也不能只扫描文件夹。应当计算：

```text
应该存在的逻辑分区
- Catalog 中已经发布且校验通过的逻辑分区
= 本次需要采集的分区
```

对于 A 股日频数据，“应该存在的日期”应来自交易日历，周末不能作为交易日展示或采集。

## 8. 基本业务流程

项目要实现的最小完整闭环：

```text
创建数据集
→ 配置采集器
→ 生成采集计划
→ 采集到临时区
→ 字段对齐与技术标准化
→ 数据质量核验
→ 按存储策略写文件
→ 原子发布
→ 更新 Catalog
```

### 8.1 首次采集

首次采集需要用户选择：

- 数据集；
- 采集器；
- 开始时间；
- 结束时间；
- 必要的供应商参数。

### 8.2 增量更新

增量更新由系统根据预期分区和 Catalog 覆盖情况自动计算未采集部分，包括历史中间缺口，而不只是最新日期之后的数据。

计划支持的任务类型：

```text
INITIAL      首次初始化
INCREMENTAL  新增数据和历史缺口补充
REPAIR       修复指定范围
REPLACE      重建指定范围
```

### 8.3 手动文件入库

手动入库不是绕过采集流程的特殊通道。任务目的与数据获取方式是两个独立维度：

```text
任务目的：INITIAL / INCREMENTAL / REPAIR / REPLACE
输入方式：COLLECTOR / FILE_IMPORT
```

手动文件入库流程：

```text
创建 FILE_IMPORT 任务
→ 上传文件到 staging
→ 记录文件名、大小和 SHA-256
→ 解析与字段对齐
→ 数据质量校验
→ 写入正式文件
→ 更新 Catalog
```

手动入库可以用于首次初始化、缺口修复或范围替换，但同样必须经过后续校验与发布流程。

### 8.4 服务器目录导入与历史迁移

浏览器上传只适合少量临时文件，不作为大规模 L2 历史数据迁移方案。历史数据先使用
`rsync`、SFTP、共享存储等系统工具迁移到 QuantStone 所在 Linux 服务器；文件传输与
QuantStone 入库是两个独立步骤。

服务器目录导入由用户显式创建任务，并调用绑定的专用目录扫描器：

```text
选择目标数据集和扫描操作
→ 扫描服务器允许访问的源目录
→ 按来源规则识别市场、日期和文件
→ 生成不可变的待导入文件清单
→ 审核文件内容和数据集契约
→ 发布或登记正式 Parquet
→ 更新 Catalog
```

不同历史来源可以使用不同扫描器，因为目录层级、文件名、压缩方式和沪深拆分规则可能
不同。扫描器只负责理解外部目录并生成清单，不以目录现状直接推断 Catalog 覆盖，也不在
系统启动时自动遍历磁盘。文件清单生成后，审核和发布继续复用数据集现有流程。

目录扫描器使用显式的 `scanner_key + operation` 注册，operation 声明目标数据集和文件名。
当前已实现 `wind_l2_sz` 扫描器，包含 `import_order` 和 `import_trade` 两个操作；源目录
必须位于数据根目录的 `imports/` 或 `QUANTSTONE_IMPORT_ROOTS` 配置的允许根目录内。
导入任务使用独立 `ImportJob` 状态：

```text
created → scanning → review_ready → importing → succeeded/failed
                                 ↘ cancelled / cancelling
```

扫描阶段按交易日期目录识别 `l2_order.parquet` / `l2_trade.parquet`，检查 Parquet Schema、
行数、分区日期和契约要求的非空字段，生成不可变清单 `imports/jobs/<job_id>/manifest.json`。
已有 Catalog 分区的日期标记为 `duplicate`，导入时跳过。执行导入前重新校验源文件大小和
mtime；文件先复制到 staging，再由 L2 审核器复核，最后复用 `publish_partition` 写正式
目录和 Catalog。导入任务和采集、合并共用同一个后台单工作线程。

当前 L2 审核器检查 Schema、空值、行数和分区日期，不对上亿行的主键组合做全量唯一性扫描；
主键唯一性应在转换脚本或一次性离线校验中确认。

## 9. 采集器原则

- 采集器负责和外部供应商、文件或下载渠道交互；
- 采集器输出先进入 staging，不得直接写正式数据目录；
- 供应商接口和目标数据集通常一一对应；
- 如果一个供应商产品以文件交付，采集器需要负责下载、解压、识别日期和文件清单；
- 百度网盘等交付方式属于采集器配置；
- 密钥、Cookie、网盘账号等敏感配置不得写入 Git；
- 采集结果必须经过对齐和核验后才能发布。

数据集在创建和启用前应已经明确目标 Schema，并绑定对应的采集器与审核器。采集任务
只选择数据集并提供本次运行参数，例如日期或供应商查询范围，不重复描述采集代码。
采集器执行数据集预先约定的获取逻辑并写入 staging；审核器随后打开暂存数据，按照
数据集契约检查字段、主键、空值、完整性和业务异常。公共审核规则可以复用，但每个
数据集允许增加专用规则。

### 9.1 采集器注册模型

采集器必须通过注册模型显式描述，不通过目录或数据集 ID 猜测实现：

```text
collector_key
└── operation
    ├── 参数定义
    ├── 执行入口
    └── 输出数据集 ID 列表
```

一个 operation 对应一个具体的可调用采集函数，注册模型不再对外增加重复的 handler
概念。数据集按照任务目的保存 `collector_key + operation` 绑定，例如首次采集和增量更新
可以分别绑定不同操作。系统根据“数据集 + 任务目的”找到采集入口，并校验 operation 的
目的与绑定一致、输出列表包含当前数据集。一个操作只声明一个输出时独立更新；声明多个
输出时自然形成联合更新，不再保存 `execution_mode`、`run_group` 或重复的 `output_key`。

采集器代码是否放在同一个文件不影响运行关系。例如 TuShare 的日线和股票列表可以由
同一个采集器注册为两个独立操作；L2 每日压缩包则注册为一个操作并声明四个输出数据集。
数据集启用时必须完成绑定存在性和输出归属的双向校验。

每个采集器在自己的模块中导出一个 `CollectorDefinition`，总注册表只显式导入并汇总，
不自动扫描目录。系统启动时校验采集器 key、operation key、可调用函数、输出数据集和
参数名称。前端只能查看已经由代码注册的采集器，不能凭空创建 Python 函数。

数据集到采集器的绑定只保存：

```text
purpose + collector_key + operation + parameters
```

其中 `parameters` 是数据集级默认参数；采集任务提供本次运行参数，系统合并后按照
operation 参数定义校验。凭证、限流和重试不属于数据集绑定关系：凭证由采集器自行读取，
限流与重试策略由 operation 注册声明，由执行框架统一执行。

当前实现已经提供代码采集器注册表，并在数据集契约中按任务目的保存操作绑定。TuShare
股票列表目前分别注册 `stock_basic_initial` 和 `stock_basic_incremental` 两个具体入口。每次快照分别
请求 `L`（上市）、`D`（退市）和 `P`（暂停上市）三种状态并合并，不能依赖空状态参数推测
“全部”。首次采集与增量更新都生成包含全部状态的完整快照。项目预置契约保留 TuShare
`stock_basic` 返回的 17 个字段；其中 `list_date` 和 `delist_date` 在落盘时技术标准化为日期类型，
其余字段保持供应商字段名与字符串语义。兼容代理若把退市股票的 `symbol` 序列化为浮点数，
采集器从同一行 `ts_code` 的点号前部分恢复代码，避免产生 `.0` 或丢失前导零；供应商原本返回
的空值保持为空，不用 `ts_code` 补值。

TuShare A 股交易日历使用数据集 ID `tushare.cn.stock.trade_cal`，默认采集 SSE 日历；TuShare
官方说明沪深北股票交易所日历一致，因此不按市场拆分。该数据集采用完整快照存储，首次采集
接受起止日期，增量更新重新生成完整快照。当前账号的 `trade_cal` 权限限制为每小时一次，
不得按年份拆成高频连续请求。

TuShare 网络入口由可选环境变量 `TUSHARE_API_URL` 统一配置，默认使用官方
`https://api.tushare.pro`。代理入口只改变传输路径，不改变供应商身份；`stock_basic`、`daily`
和 `trade_cal` 必须共享同一入口配置。运行记录的 provenance 保存实际 API URL，但不得记录 Token。

所有以日期作为逻辑分区的数据集都必须在存储策略中显式配置 `calendar_dataset_id`。系统不再
用“周一至周五”推测交易日，也不通过数据集名称隐式寻找日历。启用日期分区数据集时，所引用
的交易日历必须已创建、已启用，并且契约至少包含 `cal_date` 与 `is_open` 字段；创建采集或
手动入库任务时，日历还必须已有正式发布的快照。Planner 只为 `is_open = 1` 的日期生成运行，
并在日历缺失、文件缺失或覆盖范围不足时停止任务，向用户说明应先创建、采集或更新哪个日历。

采集器实现归属于采集能力，放在对应采集器模块中，不再放入 `datasets/` 代码目录。例如：

```text
collectors/tushare_cn_stock/
├── definition.py
├── daily.py
└── stock_basic.py
```

运行中的数据集契约保存在 Registry 数据库中。代码只为明确选入项目的常用数据集保存预置
契约，用作显式创建草稿的模板，不作为运行时契约副本。采集器目录名由采集能力决定，一个
采集器可通过多个 operation 输出多个数据集。

### 9.2 执行框架：限流与重试

所有采集调用都经过统一的执行入口，不在各采集器里手写 `sleep` 或重试循环：

```text
operation 声明 RateLimit + RetryPolicy
        ↓
run_operation：限流等待 → 调用 → 限流/网络错误按退避重试
```

- 限流按滑动窗口计算：任意 `period_seconds` 内最多放行 `calls` 次；达到上限时等待最早
  一次调用离开窗口，而不是让任务失败。
- 相同 `scope` 的操作共享同一个窗口。TuShare `daily` 的首次采集与增量更新都使用
  `scope = "daily"`，合计不超过账号限制（当前为每分钟 50 次）。
- 供应商返回限流错误时，采集器抛出可重试异常，执行框架按 `RetryPolicy` 指数退避，
  单次等待受 `max_delay_seconds` 约束；其他错误立即失败，不做无效重试。
- 网络、上游 HTTP 和供应商限流错误在重试耗尽后统一转换为中文失败原因，并同时写入任务、
  运行记录和日志。由于执行接口已经异步返回 `202`，供应商故障不再作为该 HTTP 请求的
  `500/502` 返回，而由前端轮询任务状态后展示。
- 每次限流等待和重试调度都写入结构化日志（`rate_limit_wait`、`operation_retry_scheduled`），
  便于排查长任务耗时。
- 限流器是进程内状态，多进程部署时必须改为共享限流，否则每个进程各自计算额度。

采集任务通过单进程、单工作线程的后台队列执行。`POST .../execute` 只负责把任务改为
`QUEUED` 并返回 `202`，后台线程开始处理时再改为 `RUNNING`；长日期范围不再占用原始 HTTP
请求。单工作线程用于避免多个任务同时争抢供应商限流和 SQLite 写锁。分区成功即发布并写入
Catalog，因此任务中断后新任务从 Catalog 水位继续，不会重复采集已发布分区。

## 10. 标准化与质量校验

建议按以下顺序处理：

1. 读取供应商结果；
2. 字段名映射；
3. 类型、日期、时间和编码转换；
4. 供应商特殊值与空值处理；
5. Schema 校验；
6. 主键重复检查；
7. 非空与取值范围检查；
8. 日期覆盖和预期标的覆盖检查；
9. 数据集自定义业务规则检查；
10. 生成 Validation Report。

校验失败的数据应留在 staging 或 quarantine，不得对正式 SDK 查询可见。

每个数据集默认只有一个审核器，系统直接以 `dataset_id` 查询审核器注册表，不保存额外的
`reviewer_key`。审核器代码严格映射数据集 ID，例如：

```text
reviewers/tushare/cn/stock/daily/
├── definition.py
└── reviewer.py
```

字段存在性、主键、非空和分区日期等通用检查放在 `reviewers/checks.py` 复用；每个数据集
审核器负责组合通用检查和自己的业务规则。审核器只读取 staging 文件并返回结构化报告，
不移动正式文件，也不修改 Catalog。

## 11. 逻辑分区与物理文件

必须区分：

- **逻辑分区**：系统理解和管理的最小覆盖单位，例如一个交易日；
- **物理文件**：实际存储文件，一个文件可能包含一天、一个月、一年或多个日期。

因此，即使某个数据集使用“多日单文件”，Catalog 仍应能够按交易日记录覆盖情况。

需要支持的文件组织方向：

- 单日单文件；
- 单月单文件；
- 单年单文件；
- 多日单文件；
- 增量小文件加定期合并。

Parquet 不适合原地修改。发生历史修订时，可选策略包括：

- 重写包含该分区的完整文件；
- 写增量文件，查询时合并；
- 先写增量文件，之后定期压缩合并；
- 写新版本并保留旧版本。

具体策略模型尚未最终确定，实现时应保持可扩展，不要先写死为单一方案。

### 11.1 数据集存储策略

数据集启用前应明确存储策略，至少包括逻辑分区字段、物理布局、写入策略和可选合并策略。
采集器统一产生 staging Parquet，最终文件组织由 Storage Writer 决定。当前支持的策略模型：

```text
daily                单日 Parquet
yearly_with_delta    年度主文件 + 日增量 Parquet
snapshot             完整快照 Parquet
```

TuShare 日 K 当前采用 `trade_date` 逻辑分区、`yearly_with_delta` 布局和
`replace_partition` 写入。每日数据审核通过后立即发布为 delta，Catalog 逐日登记覆盖。

物理文件已与逻辑分区分开建模：`catalog_files` 保存路径、行数、体积和校验和，
`catalog_partitions` 通过 `file_id` 指向文件，因此一个文件可以承载多个分区。统计行数、
体积和缺失文件时按文件去重，不会因为多个分区共用一个文件而重复累加。

年度合并由 `POST /api/v1/datasets/{dataset_id}/compact?year=YYYY` 提交为持久化
`MaintenanceJob`，接口立即返回 `202 + queued`。`POST .../compact-all` 会扫描 Catalog 中
尚未指向年度文件的年份，为每个待合并年份创建一个任务；已有排队或执行中任务的年份会被
跳过。前端提供“自动合并全部年份”，不需要逐年在年份输入框中提交。维护任务与采集任务共用同一个单工作线程
后台队列，避免采集和合并同时修改 Catalog 或物理文件。数据集详情负责展示最近维护任务，
前端轮询 `GET /api/v1/maintenance-jobs?dataset_id=...`；排队任务可以取消，合并一旦开始则不
允许中断，以免在文件替换临界区留下不确定状态。

后台任务读取该年所有 delta 文件，写成一份年度 Parquet，登记新文件并把整年分区指向它，旧文件移动到
`revisions/<dataset_id>/<year>/` 保留而不删除。合并的目的是减少小文件数量和读取时的
文件打开次数，不提供版本回滚或历史快照能力——需要回滚时从 revisions 目录人工恢复。

如果年度文件生成后又有单日分区被修复，再次合并必须以 Catalog 当前指向为准：读取已有
年度文件中仍由它承载的日期，排除已改指向新 delta 的旧日期，再加入最新 delta。写入前必须
校验 Catalog 中该年度的每个逻辑分区都能在合并结果中找到；不得只合并新增 delta 后让全年
分区共同指向一个不完整文件。已有年度文件覆盖前应先移入 `revisions/`。

读取时按 `file_id` 分组，每个文件只打开一次，再按分区字段过滤出行；两年数据只会打开
两个文件。合并后总行数不变，体积因减少文件头和重复字典而下降。

读取必须以 Catalog 完整性为前提：查询范围内任一 Catalog 文件不存在时，整个读取请求返回
`409` 并列出缺失路径，不得静默跳过后返回残缺数据。日期过滤应尽量下推到 Parquet/Arrow，
`limit` 在 Arrow 表阶段生效后才能转换为 Python 对象；达到行数上限后不再打开后续文件。

供应商原始文件只作为运行期临时文件。完成 Parquet 转换并记录来源元数据后删除；失败时
可短期保留并由清理策略回收。

## 12. 发布原则

- 正式文件写入成功后，才更新 Catalog；
- Catalog 更新应具有事务性；
- 文件和 Catalog 任一失败，都不能让半成品对外可见；
- 只有校验通过并成功登记 Catalog 的数据才算“已采集”；
- 历史文件被替换时应保留修订或版本线索；
- SDK 只能读取已发布数据。

发布器与审核器分离。审核通过后，通用发布服务根据数据集的 `storage_policy` 选择目标路径，
移动文件并更新 Catalog。发布代码按存储策略组织在 `publishing/`，不为每个数据集复制一套
发布器。当前已拆出路径解析、Catalog 写入和发布服务；完整的跨文件系统原子恢复仍待实现。

### 12.1 结构化日志

应用日志写入 `<data_root>/logs/application.log`，采用 JSON Lines 和大小轮转。所有包含
`job_id` 的记录同时写入 `<data_root>/logs/collection/<job_id>.log`，便于逐任务排查。
采集、审核、发布、文件暂存、API 写请求和未处理异常都应记录明确的事件名称及必要上下文。
Token、密码、Cookie、Authorization 等敏感字段在格式化阶段统一脱敏，禁止写入日志。

日志用于详细运行诊断；数据库任务、Run 和 Catalog 记录用于业务状态与审计，两者不能互相
替代。前端任务详情将两者分为“执行明细”和“运行日志”：前者展示分区状态与业务结果，
后者通过 `GET /api/v1/collection-jobs/{job_id}/logs` 读取最近的 JSON Lines 事件，展示采集、
审核、发布、限流等待和自动重试过程。日志接口只允许读取数据库中存在的任务，默认返回最近
500 条、最多 2,000 条；Token 等敏感字段仍在写入文件前统一脱敏。

## 13. 状态模型

### 13.1 数据集状态

```text
DRAFT       草稿，可修改和删除
ACTIVE      已启用，可创建采集任务
PAUSED      暂停采集
DEPRECATED  停止使用
```

当前已实现 `DRAFT` 和 `ACTIVE` 的主要行为：草稿可以修改完整契约并删除；启用后仍可修改
显示名称和说明，但数据集 ID、供应商、区域、品种、市场、现有 Schema、主键、采集绑定和
存储策略保持不可直接修改。实质契约变化必须创建独立的新数据集，不能覆盖已有契约和已发布
数据；新旧数据集不维护版本关系。

### 13.2 数据集物理删除

数据集删除采用两阶段流程，且所有状态的数据集都必须使用同一流程：

1. 用户可以在目录中批量选择数据集；
2. 后端生成影响审查，汇总任务、运行、Catalog、行数、物理文件数和空间；
3. 存在排队、运行或取消中的任务时禁止删除；
4. 数据集仍被未纳入本次删除的日期分区数据集作为交易日历引用时禁止删除；
5. 审查返回与当前影响快照绑定的令牌和完整确认文字；执行时重新审查，状态变化会使令牌失效；
6. 用户必须原样输入包含全部数据集 ID 的确认文字；
7. 文件先移动到数据根目录内的临时删除区，数据库提交失败时恢复文件，提交成功后再最终清除。

删除范围包括数据集及字段契约、采集任务与运行、维护任务、Catalog 文件与分区记录、任务日志、
staging、正式数据目录和 revisions。应用公共日志不会随单个数据集删除。旧的单数据集直接删除接口
不得绕过审查流程。

### 13.3 采集任务状态（规划）

```text
CREATED
→ PLANNING
→ FETCHING
→ NORMALIZING
→ VALIDATING
→ WRITING
→ PUBLISHING
→ SUCCEEDED
```

任一步失败进入：

```text
FAILED 或 QUARANTINED
```

任务状态和数据分区状态应分别管理。

当前手动文件导入已先实现两个输入准备状态：

```text
AWAITING_FILE  等待用户上传文件
STAGED         文件已进入 staging，尚未校验和发布
```

执行期状态已实现：

```text
QUEUED       已进入后台队列，等待工作线程
RUNNING      正在执行采集
CANCELLING   已请求取消，等待当前分区处理完成
CANCELLED    已取消
```

- 排队任务可以在开始前直接取消；进入执行后采用协作式取消。
- 取消是协作式的：执行器在每个分区开始前检查取消请求，当前分区完成后停止；已发布分区
  保留在 Catalog 中，不会被回滚。取消请求先登记在进程内，再尝试持久化 `cancelling`；
  SQLite 状态写入遇到短暂锁冲突时不阻断取消，工作线程会在分区边界写回 `cancelled`。
  日常执行在调用供应商前提交分区开始状态，避免长事务阻塞取消等写操作。
- 快照类任务只有一次供应商调用，调用期间不持有 SQLite 写事务；取消请求可以同时落库，
  并在供应商调用返回后、审核后和发布前的边界生效。取消后删除本次 staging，不审核、不
  发布，任务和运行记录都进入 `CANCELLED`。任务一旦进入发布临界区则拒绝取消，避免成功
  发布后被覆盖成 `CANCELLING`。
- 任务进度由分区运行记录统计：`GET /api/v1/collection-jobs/{id}/progress` 返回预期分区
  总数（来自交易日历）、已发布数、失败数、最新分区和百分比。进度接口同时返回
  `started_at`、`finished_at`、`elapsed_seconds`、`eta_seconds`、`expected_finish_at` 和
  `eta_basis`：日分区任务按已处理分区的平均耗时估算剩余时间；快照任务使用同一
  `collector_operation` 最近成功任务的中位耗时；样本不足时只标记为 `insufficient_data`，
  不虚构完成时间。
- 任务记录接口使用 `limit` / `offset` 分页并返回 `total`，默认 20 条、最大 200 条；
  分区运行明细同样分页，默认 100 条、按分区倒序，前端通过“加载更多”读取更早分区。
  翻页和轮询只刷新当前页，不重复拉取全部历史记录。
- 任务记录可以删除，但只允许在非执行状态下删除；删除只移除任务和运行记录，不删除已
  发布的 Parquet 文件与 Catalog 记录。
- 任务记录保存任务级 `error`。所有采集执行路径都必须在异常退出时将任务持久化为
  `FAILED`，不能只依赖 HTTP 响应或日志；前端在任务明细中直接展示该错误。
- 应用启动时将上次进程遗留的 `QUEUED`、`RUNNING`、`CANCELLING` 任务标记为 `FAILED`，并说明任务因
  应用重启而中断。已经成功发布的分区仍然保留，后续通过新任务从 Catalog 水位继续。
- “重试”不修改原任务。失败、审核异常或已取消的采集器任务可以复制为一条新的 `CREATED`
  任务，新任务通过 `retry_of_job_id` 指向原任务，并完整保留原任务当时已经解析完成的采集器、
  operation、日期和参数。前端点击一次“重试”后创建该任务并立即执行；原失败任务继续保留
  错误和运行记录用于审计。
- 新启用且尚无已发布 Catalog 分区的数据集必须先完成一次 `initial` 任务。首次任务成功发布
  前，API 拒绝创建 `incremental`、`repair` 和 `replace` 任务；已有正式分区的数据集视为已完成
  初始化，以兼容迁移进来的历史数据。数据集详情直接展示契约中绑定的采集操作，并根据该
  状态启用“首次采集”或后续操作。

## 14. SDK 原则

第一阶段 SDK 应提供通用数据集访问，而不是假装所有供应商可以互换：

```python
client.describe("tushare.cn.stock.daily")
client.schema("tushare.cn.stock.daily")
client.coverage("tushare.cn.stock.daily")
client.read(
    "tushare.cn.stock.daily",
    start="2026-01-01",
    end="2026-11-17",
)
```

SDK 不应暗中拼接其他数据集或补充字段。

如果上层回测或实盘系统需要稳定统一接口，应由上层转换器或 Repository 层实现。是否在未来提供共享语义 SDK 仍为待定事项。

## 15. 代码、元数据与真实数据分离

代码仓库只保存：

- 源代码；
- 数据库迁移；
- 配置模板；
- 文档；
- 测试和少量测试样本。

真实金融数据不放在 Git 仓库中，应存放在用户配置的外部数据根目录或其他存储介质。

建议 Catalog 不保存写死的绝对路径，而保存：

```text
storage_id + relative_path
```

这样可以在不同机器、硬盘或 NAS 之间迁移。

外部数据目录的规划方向：

```text
<data_root>/
├── catalog/
├── datasets/
├── staging/
├── quarantine/
├── revisions/
└── logs/
```

该目录结构尚未正式实现，最终设计应结合 Catalog 和存储策略模块确定。

## 18. 前端产品约定

- 左侧导航可以收起为图标栏，状态保存在浏览器本地；收起后鼠标悬停显示文字提示。
- 默认使用中文界面；
- 使用清晰的无衬线字体；
- 数字指标不使用装饰性衬线字体；
- 数据目录按品种组织，不复制其他系统的 L0/L1 数据分级；
- A 股基础信息、日线、分钟、逐笔等本质上都属于 A 股股票数据，应在品种层面保持同组；
- ETF、期货、港股等可以作为不同品种或区域展示；
- 市场只在确实影响数据契约时强调。

存储概览与 Catalog 分区查询保留为后端 API，但前端不再提供“数据存储”入口：物理文件路径
属于实现细节，不应作为产品界面暴露。正式覆盖信息必须来自 Catalog；后端可以检查 Catalog
所指文件是否存在，但不得通过扫描目录反向猜测数据覆盖。将来的覆盖概览应围绕数据集和
交易日展示，而不是罗列 Parquet 文件。

默认首页是“数据概览”，以数据卡形式按数据集聚合：分区数、行数、体积、日期覆盖率和最新
分区。覆盖率由已发布分区数与交易日历中的交易日数共同计算，不读取物理文件目录；分母取
该数据集最早 Catalog 分区到今天之间 `is_open = 1` 的交易日，不使用某次采集任务填写的
日期范围。数据卡可以点开进入数据集详情。

数据概览同时提供“采集概览”：当前执行中、排队中、等待文件、最近 24 小时成功/失败数、
最近完成时间和最近 5 次采集任务；点击任务行进入采集页并自动展开该任务，而不是数据集
详情。该区域直接聚合 `CollectionJob`，不依赖前端加载完整任务列表。采集概览面板常显，
其中“最近采集任务”列表默认收起，点击该行展开。

数据概览还提供“日更数据完成率”：只统计 `update_frequency = daily` 的数据集，按日分区
数据集显示最新交易日状态，以及最近 30 个交易日的完成率、缺失数、失败数和待采集数；
日更快照数据集（如股票列表）按最近一次成功发布/采集是否覆盖最新交易日判断“已更新/需
更新”。月更数据集（如交易日历）不进入该面板。分母排除当天“待采集”状态；完成状态来自
Catalog 与采集运行记录，不扫描物理目录。明细默认收起，点击“完成率明细”展开。

数据集卡片在状态徽标左侧提供快捷操作：尚无已发布分区时显示“首次采集”，已经有
Catalog 分区时只显示“增量更新”；点击后创建任务并立即提交后台执行，不跳转采集页。
需要必填参数的采集操作会先弹出参数对话框。快捷操作仍使用数据集已绑定的采集器与
operation，并遵守任务创建校验，不绕过正常采集流程。快照等不按交易日分区的数据集也显示
覆盖率条：已发布快照显示 100%，尚未初始化显示 0%。标记为历史数据集的数据集不进入
覆盖热力图和日更完成率。

数据集详情提供“数据预览”面板。未填写筛选条件时固定展示 20 行 Catalog 已发布数据；填写
任意主键字段后进入查询模式，允许使用联合主键的部分字段精确筛选，最多返回 100,000 行。
查询结果超过上限时返回准确匹配总数并明确标记截断。预览不得读取 staging 或绕过 Catalog
扫描文件；也不允许使用非主键字段筛选。尚未正式发布的数据集明确显示为空，读取失败时在
面板内显示后端返回的具体原因，包括缺失的 Catalog 文件路径。结果表格使用固定高度的内部
滚动区域和虚拟行，只渲染当前视口附近的数据，避免大结果集生成等量 DOM 节点并撑长页面。
完成主键筛选后可以把全部匹配结果下载为 CSV 或 Parquet；下载不受 100,000 行预览上限影响，
但必须至少提供一个主键条件，禁止从预览面板无条件导出整个数据集。服务端导出文件只作临时
响应文件，下载完成后立即删除，不进入 Catalog。

概览页顶部是覆盖热力图：

- 纵轴：绑定了交易日历、按日分区的数据集；快照数据集不进入热力图；
- 横轴：交易日历中 `is_open = 1` 的日期，默认最近 90 个交易日，可切换 30 / 90 / 250；
- 单元状态与优先级：文件异常 > 完整 > 采集失败 > 缺失；当天尚未采集记为“待采集”；
- 横轴只包含今天及以前的交易日，不展示未来日期；
- 采集失败只统计未取消任务产生的失败运行，取消任务的残留运行不算数据问题；
- 热力图数据必须来自 Catalog、采集运行记录和交易日历，不扫描数据目录。

## 19. 推荐开发顺序

推荐按端到端纵向闭环推进，而不是先把所有模块空壳建完：

1. **Registry**：继续补充采集、分区、存储、质量策略；
2. **Collection Job**：任务模型和首次/增量/修复计划；
3. **一个模拟采集器**：先不依赖外部账号；
4. **Staging 与标准化**：保存采集结果并对齐类型；
5. **Validation**：Schema、主键、空值和覆盖检查；
6. **Storage Writer**：先实现一种简单 Parquet 策略；
7. **Catalog 与原子发布**：登记分区、文件和质量结果；
8. **SDK 读取**：按数据集和时间范围读取已发布数据；
9. **真实采集器**：TuShare、L2 文件/百度网盘等；
10. **概览与覆盖热力图**。

第一个完整样例可以选用：

```text
tb_l2.cn.stock.l2_order.sh
```

但如果真实 L2 文件格式尚不稳定，应先使用模拟采集器跑通闭环，再接入真实数据。

## 20. 后续 Agent 开发约束

后续 Agent 在修改项目前应遵守：

1. 不要擅自引入跨供应商统一业务 Schema；
2. 不要把淘宝或百度网盘直接当成供应商身份；
3. 不要把真实数据文件或密钥提交到 Git；
4. 不要让采集器直接写正式数据目录；
5. 不要通过扫描文件夹代替 Catalog；
6. 不要把逻辑分区和物理文件视为同一个概念；
7. 不要在 SDK 内隐式拼接数据集；
8. 不要将周末当作 A 股交易日；
9. 不得覆盖已启用数据集的实质契约；变化时创建独立的新数据集；
10. 新功能应包含与风险相匹配的测试，并更新相关中文文档；
11. 提交前运行后端测试、Ruff 和前端构建；
12. 保持提交范围清晰，不混入无关改动。

## 21. 尚未最终确定的事项

以下内容仍应保留讨论空间：

- 供应商注册表的具体结构；
- 采集器插件接口；
- 交易日历的权威来源；
- 逻辑分区粒度配置模型；
- 单日、多日、月度和年度文件策略的配置方式；
- 历史修订采用 Copy-on-Write、增量文件还是混合方式；
- Catalog 表结构；
- 原子发布和崩溃恢复方案；
- SDK 的包名、查询接口和返回类型；
- 是否以及何时提取共享数据转换器；
- SQLite 之外是否需要 PostgreSQL；
- 何时将当前单进程后台队列升级为独立 Worker 和持久化消息队列。

Agent 不应把这些待定事项描述成已确定方案。可以先实现最小可替换接口，再根据真实数据和使用体验确定。
