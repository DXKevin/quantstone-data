# QuantStone Data：项目架构、设计原则与开发约定

本文档用于向后续开发者和 Agent 说明 QuantStone Data 的项目定位、已经确定的架构原则、当前实现状态及尚未确定的事项。

阅读时请特别区分：

- **已确定原则**：后续实现应遵守，除非用户明确改变决定。
- **当前实现**：代码库中已经存在并通过测试的功能。
- **规划方向**：可以指导设计，但不代表已经实现。
- **待定事项**：不要擅自固化，应在实现前与用户确认或保持可扩展。

## 1. 项目定位

项目名称：`quantstone-data`  
产品名称：**QuantStone Data**

QuantStone Data 是一套面向个人量化研究的数据基础设施，用于：

- 注册和描述金融数据集；
- 从不同供应商采集数据；
- 对采集结果进行字段对齐和质量校验；
- 管理数据文件、覆盖范围、修订和版本；
- 通过 API 和 SDK 提供稳定的数据发现与读取能力。

QuantStone 可以作为未来一组量化基础设施项目的总品牌。回测系统、因子系统和实盘系统可以成为独立的上层项目，不应直接塞入 `quantstone-data`。

## 2. 最重要的架构结论

### 2.1 统一管理，不强制统一业务结构

本项目遵循：

> 统一管理数据集，但不强制统一不同供应商的数据业务结构。

数据集契约要求单个数据集的字段和语义明确、稳定、可追踪，但不要求不同供应商的数据集具有相同字段。

例如可以同时存在：

```text
tushare.cn.stock.daily
tushare.cn.stock.stk_limit
tushare.cn.stock.stock_basic
ths.cn.stock.daily
```

其中，同花顺日线可以直接包含 ST、涨跌停价等字段；TuShare 可以将这些内容放在不同接口、不同数据集中。本项目不强行将它们合并成一个统一日线表。

### 2.2 供应商接口可以直接决定数据集边界

对于具有明确 API 的供应商，通常采用“一项供应商接口对应一个数据集”的方式。

对于没有标准 API、通过文件交付的数据产品，按照供应商实际提供的数据产品和文件语义划分数据集。

数据集 ID 可以使用供应商 API 名称；频率、接口参数和更新周期等内容作为元数据保存，不必全部重复写入 ID。

### 2.3 统一结构由上层项目按需建立

跨供应商组合和转换不属于数据库层的强制职责。例如回测项目可以自行定义：

```text
tushare.daily
+ tushare.stk_limit
+ tushare.st_status
        ↓
BacktestDailyBar
```

同花顺日线则可能直接转换为 `BacktestDailyBar`。

如果多个上层项目反复使用同一种转换，可将转换器提取为共享库；现阶段不应提前在数据层维护大规模统一金融数据模型。

### 2.4 允许最低限度的技术标准化

不统一业务字段，不代表完全原样保存接口响应。为了可靠存储，可以进行必要的技术处理，例如：

- 将日期字符串转换为 `date`；
- 将时间转换为明确的时间类型；
- 统一字符编码；
- 明确空值表示；
- 转换为 Parquet 支持的数据类型；
- 保证数值精度；
- 记录供应商原字段名和存储字段名。

不得在没有数据集契约说明的情况下，擅自改变字段业务含义或暗中拼接其他数据集。

## 3. 项目职责边界

### 3.1 QuantStone Data 负责

- 数据集注册和 Schema 管理；
- 供应商与数据集元数据管理；
- 首次采集、增量更新和指定范围修复；
- 原始结果进入临时区；
- 字段类型转换和技术标准化；
- 数据契约与质量校验；
- 文件写入、覆盖范围、版本和修订管理；
- 数据目录、运行记录、错误和隔离数据管理；
- 通用 API/SDK：发现数据集、查看 Schema、查看覆盖、读取数据。

### 3.2 QuantStone Data 暂不负责

- 强制统一不同供应商的业务字段；
- 自动构建跨供应商统一日线；
- 为研究生成大量宽表；
- 因子计算；
- 回测引擎；
- 实盘交易；
- 针对某个上层系统的专用业务数据结构。

## 4. 数据集 ID 规则

固定格式：

```text
<provider>.<region>.<instrument>.<dataset>[.<market>]
```

含义：

- `provider`：实际供应商或数据产品的稳定代号；
- `region`：数据区域，例如 `cn`、`hk`；
- `instrument`：品种，例如 `stock`、`etf`、`futures`、`option`；
- `dataset`：供应商 API 名称或供应商定义的数据集名称；
- `market`：可选，仅在不同市场必须使用不同契约时添加。

规则：

- 全部使用小写 ASCII；
- `.` 表示分类层级；
- 同一层级的复合名称使用 `_`；
- ID 一经创建原则上不修改；
- 字段结构变化通过 `schema_version` 表示，不把版本写进 ID；
- 市场不是固定必填层级，只有需要时才追加。

示例：

```text
tushare.cn.stock.daily
tushare.cn.stock.stk_limit
ths.cn.stock.daily
tb_l2.cn.stock.l2_order.sh
tb_l2.cn.stock.l2_order.sz
tb_l2.cn.stock.l2_trade.sh
tb_l2.cn.stock.l2_trade.sz
```

详细规则见 [数据集 ID 命名规范](dataset-id.md)。

## 5. L2 数据的特殊约定

当前讨论中的 L2 数据：

- 通过淘宝购买；
- 通过百度网盘下载和更新；
- 上海与深圳字段或语义不同；
- 分为逐笔委托和逐笔成交。

约定：

- 淘宝是购买渠道，不是供应商身份；
- 百度网盘是交付方式，不是供应商身份；
- `provider` 应代表具体卖家或具体数据产品的稳定代号；
- 上海、深圳需要不同数据契约，因此拆分数据集；
- 逐笔委托使用 `l2_order`；
- 逐笔成交使用 `l2_trade`，不使用含义不够清晰的 `tran`；
- 上海使用 `sh`，深圳使用 `sz`。

最终形成四个数据集：

```text
<provider>.cn.stock.l2_order.sh
<provider>.cn.stock.l2_order.sz
<provider>.cn.stock.l2_trade.sh
<provider>.cn.stock.l2_trade.sz
```

## 6. 数据集契约

每个注册数据集至少应描述：

- 数据集 ID；
- 显示名称和说明；
- 供应商；
- 区域；
- 品种；
- 数据集/API 名称；
- 可选市场；
- Schema 版本；
- 字段名称、类型、含义、单位、供应商原字段名；
- 是否允许为空；
- 主键或唯一键；
- 时间字段；
- 数据粒度；
- 采集参数和时间范围能力；
- 逻辑分区规则；
- 物理文件组织策略；
- 更新和修订策略；
- 完整性与质量规则；
- 供应商接口或产品版本。

当前实现只覆盖其中的核心身份信息、Schema、字段、主键和时间字段。采集、分区、存储和质量策略将在后续模块中增加。

## 7. Registry 与 Catalog

这两个概念必须分开：

### 7.1 Dataset Registry

Registry 描述“数据应该是什么”：

- 数据集定义；
- Schema 版本；
- 字段契约；
- 主键和时间字段；
- 采集、存储和校验策略。

### 7.2 Data Catalog

Catalog 描述“实际上已经有什么”：

- 已发布的逻辑分区；
- 日期覆盖范围和缺口；
- 对应物理文件；
- 行数、大小、校验和；
- 数据版本和修订；
- 采集任务和发布时间；
- 数据质量结果。

增量更新不能简单使用“最大日期加一天”，也不能只扫描文件夹。应当计算：

```text
应该存在的逻辑分区
- Catalog 中已经发布且校验通过的逻辑分区
= 本次需要采集的分区
```

对于 A 股日频数据，“应该存在的日期”应来自交易日历，周末不能作为交易日展示或采集。

## 8. 基本业务流程

项目要实现的最小完整闭环：

```text
创建数据集
→ 配置采集器
→ 生成采集计划
→ 采集到临时区
→ 字段对齐与技术标准化
→ 数据质量核验
→ 按存储策略写文件
→ 原子发布
→ 更新 Catalog
```

### 8.1 首次采集

首次采集需要用户选择：

- 数据集；
- 采集器；
- 开始时间；
- 结束时间；
- 必要的供应商参数。

### 8.2 增量更新

增量更新由系统根据预期分区和 Catalog 覆盖情况自动计算未采集部分，包括历史中间缺口，而不只是最新日期之后的数据。

计划支持的任务类型：

```text
INITIAL      首次初始化
INCREMENTAL  新增数据和历史缺口补充
REPAIR       修复指定范围
REPLACE      重建指定范围
```

### 8.3 手动文件入库

手动入库不是绕过采集流程的特殊通道。任务目的与数据获取方式是两个独立维度：

```text
任务目的：INITIAL / INCREMENTAL / REPAIR / REPLACE
输入方式：COLLECTOR / FILE_IMPORT
```

手动文件入库流程：

```text
创建 FILE_IMPORT 任务
→ 上传文件到 staging
→ 记录文件名、大小和 SHA-256
→ 解析与字段对齐
→ 数据质量校验
→ 写入正式文件
→ 更新 Catalog
```

手动入库可以用于首次初始化、缺口修复或范围替换，但同样必须经过后续校验与发布流程。

## 9. 采集器原则

- 采集器负责和外部供应商、文件或下载渠道交互；
- 采集器输出先进入 staging，不得直接写正式数据目录；
- 供应商接口和目标数据集通常一一对应；
- 如果一个供应商产品以文件交付，采集器需要负责下载、解压、识别日期和文件清单；
- 百度网盘等交付方式属于采集器配置；
- 密钥、Cookie、网盘账号等敏感配置不得写入 Git；
- 采集结果必须经过对齐和核验后才能发布。

数据集在创建和启用前应已经明确目标 Schema，并绑定对应的采集器与审核器。采集任务
只选择数据集并提供本次运行参数，例如日期或供应商查询范围，不重复描述采集代码。
采集器执行数据集预先约定的获取逻辑并写入 staging；审核器随后打开暂存数据，按照
数据集契约检查字段、主键、空值、完整性和业务异常。公共审核规则可以复用，但每个
数据集允许增加专用规则。

### 9.1 采集器注册模型

采集器必须通过注册模型显式描述，不通过目录或数据集 ID 猜测实现：

```text
collector_key
└── operation
    ├── 参数定义
    ├── 执行入口
    └── 输出数据集 ID 列表
```

一个 operation 对应一个具体的可调用采集函数，注册模型不再对外增加重复的 handler
概念。数据集按照任务目的保存 `collector_key + operation` 绑定，例如首次采集和增量更新
可以分别绑定不同操作。系统根据“数据集 + 任务目的”找到采集入口，并校验 operation 的
目的与绑定一致、输出列表包含当前数据集。一个操作只声明一个输出时独立更新；声明多个
输出时自然形成联合更新，不再保存 `execution_mode`、`run_group` 或重复的 `output_key`。

采集器代码是否放在同一个文件不影响运行关系。例如 TuShare 的日线和股票列表可以由
同一个采集器注册为两个独立操作；L2 每日压缩包则注册为一个操作并声明四个输出数据集。
数据集启用时必须完成绑定存在性和输出归属的双向校验。

每个采集器在自己的模块中导出一个 `CollectorDefinition`，总注册表只显式导入并汇总，
不自动扫描目录。系统启动时校验采集器 key、operation key、可调用函数、输出数据集和
参数名称。前端只能查看已经由代码注册的采集器，不能凭空创建 Python 函数。

数据集到采集器的绑定只保存：

```text
purpose + collector_key + operation + parameters
```

其中 `parameters` 是数据集级默认参数；采集任务提供本次运行参数，系统合并后按照
operation 参数定义校验。凭证、限流和重试不属于数据集绑定关系：凭证由采集器自行读取，
限流与重试策略由 operation 注册声明，由执行框架统一执行。

当前实现已经提供代码采集器注册表，并在数据集契约中按任务目的保存操作绑定。TuShare
股票列表目前分别注册 `stock_list_initial` 和 `stock_list_incremental` 两个具体入口。首版只采集 TuShare 默认的当前上市状态 `L`，
其他上市状态需要等通用任务参数和供应商限流调度完成后开放。

TuShare A 股交易日历使用数据集 ID `tushare.cn.stock.trade_cal`，默认采集 SSE 日历；TuShare
官方说明沪深北股票交易所日历一致，因此不按市场拆分。该数据集采用完整快照存储，首次采集
接受起止日期，增量更新重新生成完整快照。当前账号的 `trade_cal` 权限限制为每小时一次，
不得按年份拆成高频连续请求。

所有以日期作为逻辑分区的数据集都必须在存储策略中显式配置 `calendar_dataset_id`。系统不再
用“周一至周五”推测交易日，也不通过数据集名称隐式寻找日历。启用日期分区数据集时，所引用
的交易日历必须已创建、已启用，并且契约至少包含 `cal_date` 与 `is_open` 字段；创建采集或
手动入库任务时，日历还必须已有正式发布的快照。Planner 只为 `is_open = 1` 的日期生成运行，
并在日历缺失、文件缺失或覆盖范围不足时停止任务，向用户说明应先创建、采集或更新哪个日历。

采集器实现归属于采集能力，放在对应采集器模块中，不再放入 `datasets/` 代码目录。例如：

```text
collectors/tushare_cn_stock/
├── definition.py
├── daily.py
└── stock_basic.py
```

数据集契约保存在 Registry 数据库中；代码不再重复保存一套数据集定义。采集器目录名由
采集能力决定，一个采集器可通过多个 operation 输出多个数据集。

### 9.2 执行框架：限流与重试

所有采集调用都经过统一的执行入口，不在各采集器里手写 `sleep` 或重试循环：

```text
operation 声明 RateLimit + RetryPolicy
        ↓
run_operation：限流等待 → 调用 → 限流/网络错误按退避重试
```

- 限流按滑动窗口计算：任意 `period_seconds` 内最多放行 `calls` 次；达到上限时等待最早
  一次调用离开窗口，而不是让任务失败。
- 相同 `scope` 的操作共享同一个窗口。TuShare `daily` 的首次采集与增量更新都使用
  `scope = "daily"`，合计不超过账号限制（当前为每分钟 50 次）。
- 供应商返回限流错误时，采集器抛出可重试异常，执行框架按 `RetryPolicy` 指数退避，
  单次等待受 `max_delay_seconds` 约束；其他错误立即失败，不做无效重试。
- 每次限流等待和重试调度都写入结构化日志（`rate_limit_wait`、`operation_retry_scheduled`），
  便于排查长任务耗时。
- 限流器是进程内状态，多进程部署时必须改为共享限流，否则每个进程各自计算额度。

任务仍同步执行，长日期范围会占用一次 HTTP 请求。分区成功即发布并写入 Catalog，因此
任务中断后新任务从 Catalog 水位继续，不会重复采集已发布分区。

## 10. 标准化与质量校验

建议按以下顺序处理：

1. 读取供应商结果；
2. 字段名映射；
3. 类型、日期、时间和编码转换；
4. 供应商特殊值与空值处理；
5. Schema 校验；
6. 主键重复检查；
7. 非空与取值范围检查；
8. 日期覆盖和预期标的覆盖检查；
9. 数据集自定义业务规则检查；
10. 生成 Validation Report。

校验失败的数据应留在 staging 或 quarantine，不得对正式 SDK 查询可见。

每个数据集默认只有一个审核器，系统直接以 `dataset_id` 查询审核器注册表，不保存额外的
`reviewer_key`。审核器代码严格映射数据集 ID，例如：

```text
reviewers/tushare/cn/stock/daily/
├── definition.py
└── reviewer.py
```

字段存在性、主键、非空和分区日期等通用检查放在 `reviewers/checks.py` 复用；每个数据集
审核器负责组合通用检查和自己的业务规则。审核器只读取 staging 文件并返回结构化报告，
不移动正式文件，也不修改 Catalog。

## 11. 逻辑分区与物理文件

必须区分：

- **逻辑分区**：系统理解和管理的最小覆盖单位，例如一个交易日；
- **物理文件**：实际存储文件，一个文件可能包含一天、一个月、一年或多个日期。

因此，即使某个数据集使用“多日单文件”，Catalog 仍应能够按交易日记录覆盖情况。

需要支持的文件组织方向：

- 单日单文件；
- 单月单文件；
- 单年单文件；
- 多日单文件；
- 增量小文件加定期合并。

Parquet 不适合原地修改。发生历史修订时，可选策略包括：

- 重写包含该分区的完整文件；
- 写增量文件，查询时合并；
- 先写增量文件，之后定期压缩合并；
- 写新版本并保留旧版本。

具体策略模型尚未最终确定，实现时应保持可扩展，不要先写死为单一方案。

### 11.1 数据集存储策略

数据集启用前应明确存储策略，至少包括逻辑分区字段、物理布局、写入策略和可选合并策略。
采集器统一产生 staging Parquet，最终文件组织由 Storage Writer 决定。当前支持的策略模型：

```text
daily                单日 Parquet
yearly_with_delta    年度主文件 + 日增量 Parquet
snapshot             完整快照 Parquet
```

TuShare 日 K 当前采用 `trade_date` 逻辑分区、`yearly_with_delta` 布局和
`replace_partition` 写入。每日数据审核通过后立即发布为 delta，Catalog 逐日登记覆盖。

物理文件已与逻辑分区分开建模：`catalog_files` 保存路径、行数、体积和校验和，
`catalog_partitions` 通过 `file_id` 指向文件，因此一个文件可以承载多个分区。统计行数、
体积和缺失文件时按文件去重，不会因为多个分区共用一个文件而重复累加。

年度合并由 `POST /api/v1/datasets/{dataset_id}/compact?year=YYYY` 触发：读取该年所有
delta 文件，写成一份年度 Parquet，登记新文件并把整年分区指向它，旧文件移动到
`revisions/<dataset_id>/<year>/` 保留而不删除。合并的目的是减少小文件数量和读取时的
文件打开次数，不提供版本回滚或历史快照能力——需要回滚时从 revisions 目录人工恢复。

读取时按 `file_id` 分组，每个文件只打开一次，再按分区字段过滤出行；两年数据只会打开
两个文件。合并后总行数不变，体积因减少文件头和重复字典而下降。

供应商原始文件只作为运行期临时文件。完成 Parquet 转换并记录来源元数据后删除；失败时
可短期保留并由清理策略回收。

## 12. 发布原则

- 正式文件写入成功后，才更新 Catalog；
- Catalog 更新应具有事务性；
- 文件和 Catalog 任一失败，都不能让半成品对外可见；
- 只有校验通过并成功登记 Catalog 的数据才算“已采集”；
- 历史文件被替换时应保留修订或版本线索；
- SDK 只能读取已发布数据。

发布器与审核器分离。审核通过后，通用发布服务根据数据集的 `storage_policy` 选择目标路径，
移动文件并更新 Catalog。发布代码按存储策略组织在 `publishing/`，不为每个数据集复制一套
发布器。当前已拆出路径解析、Catalog 写入和发布服务；完整的跨文件系统原子恢复仍待实现。

### 12.1 结构化日志

应用日志写入 `<data_root>/logs/application.log`，采用 JSON Lines 和大小轮转。所有包含
`job_id` 的记录同时写入 `<data_root>/logs/collection/<job_id>.log`，便于逐任务排查。
采集、审核、发布、文件暂存、API 写请求和未处理异常都应记录明确的事件名称及必要上下文。
Token、密码、Cookie、Authorization 等敏感字段在格式化阶段统一脱敏，禁止写入日志。

日志用于详细运行诊断；数据库任务、Run 和 Catalog 记录用于业务状态与审计，两者不能互相
替代。

## 13. 状态模型

### 13.1 数据集状态

```text
DRAFT       草稿，可修改和删除
ACTIVE      已启用，可创建采集任务
PAUSED      暂停采集
DEPRECATED  停止使用
```

当前已实现 `DRAFT` 和 `ACTIVE` 的主要行为：草稿可以修改和删除，启用后不能直接修改现有 Schema。

### 13.2 采集任务状态（规划）

```text
CREATED
→ PLANNING
→ FETCHING
→ NORMALIZING
→ VALIDATING
→ WRITING
→ PUBLISHING
→ SUCCEEDED
```

任一步失败进入：

```text
FAILED 或 QUARANTINED
```

任务状态和数据分区状态应分别管理。

当前手动文件导入已先实现两个输入准备状态：

```text
AWAITING_FILE  等待用户上传文件
STAGED         文件已进入 staging，尚未校验和发布
```

执行期状态已实现：

```text
RUNNING      正在执行采集
CANCELLING   已请求取消，等待当前分区处理完成
CANCELLED    已取消
```

- 取消是协作式的：执行器在每个分区开始前检查取消请求，当前分区完成后停止；已发布分区
  保留在 Catalog 中，不会被回滚。
- 快照类任务只有一次供应商调用，取消在调用返回后生效，主要用于避免继续后续步骤。
- 任务进度由分区运行记录统计：`GET /api/v1/collection-jobs/{id}/progress` 返回预期分区
  总数（来自交易日历）、已发布数、失败数、最新分区和百分比。
- 任务记录可以删除，但只允许在非执行状态下删除；删除只移除任务和运行记录，不删除已
  发布的 Parquet 文件与 Catalog 记录。

## 14. SDK 原则

第一阶段 SDK 应提供通用数据集访问，而不是假装所有供应商可以互换：

```python
client.describe("tushare.cn.stock.daily")
client.schema("tushare.cn.stock.daily")
client.coverage("tushare.cn.stock.daily")
client.read(
    "tushare.cn.stock.daily",
    start="2026-01-01",
    end="2026-11-17",
)
```

SDK 不应暗中拼接其他数据集或补充字段。

如果上层回测或实盘系统需要稳定统一接口，应由上层转换器或 Repository 层实现。是否在未来提供共享语义 SDK 仍为待定事项。

## 15. 代码、元数据与真实数据分离

代码仓库只保存：

- 源代码；
- 数据库迁移；
- 配置模板；
- 文档；
- 测试和少量测试样本。

真实金融数据不放在 Git 仓库中，应存放在用户配置的外部数据根目录或其他存储介质。

建议 Catalog 不保存写死的绝对路径，而保存：

```text
storage_id + relative_path
```

这样可以在不同机器、硬盘或 NAS 之间迁移。

外部数据目录的规划方向：

```text
<data_root>/
├── catalog/
├── datasets/
├── staging/
├── quarantine/
├── revisions/
└── logs/
```

该目录结构尚未正式实现，最终设计应结合 Catalog 和存储策略模块确定。

## 18. 前端产品约定

- 默认使用中文界面；
- 使用清晰的无衬线字体；
- 数字指标不使用装饰性衬线字体；
- 数据目录按品种组织，不复制其他系统的 L0/L1 数据分级；
- A 股基础信息、日线、分钟、逐笔等本质上都属于 A 股股票数据，应在品种层面保持同组；
- ETF、期货、港股等可以作为不同品种或区域展示；
- 市场只在确实影响数据契约时强调。

存储概览与 Catalog 分区查询保留为后端 API，但前端不再提供“数据存储”入口：物理文件路径
属于实现细节，不应作为产品界面暴露。正式覆盖信息必须来自 Catalog；后端可以检查 Catalog
所指文件是否存在，但不得通过扫描目录反向猜测数据覆盖。将来的覆盖概览应围绕数据集和
交易日展示，而不是罗列 Parquet 文件。

默认首页是“数据概览”，以数据卡形式按数据集聚合：分区数、行数、体积、日期覆盖率和最新
分区。覆盖率由已发布分区数与交易日历中的交易日数共同计算，不读取物理文件目录。数据卡
可以点开进入数据集详情。

概览页顶部是覆盖热力图：

- 纵轴：绑定了交易日历、按日分区的数据集；快照数据集不进入热力图；
- 横轴：交易日历中 `is_open = 1` 的日期，默认最近 90 个交易日，可切换 30 / 90 / 250；
- 单元状态与优先级：文件异常 > 完整 > 采集失败 > 缺失；当天尚未采集记为“待采集”；
- 横轴只包含今天及以前的交易日，不展示未来日期；
- 采集失败只统计未取消任务产生的失败运行，取消任务的残留运行不算数据问题；
- 热力图数据必须来自 Catalog、采集运行记录和交易日历，不扫描数据目录。

## 19. 推荐开发顺序

推荐按端到端纵向闭环推进，而不是先把所有模块空壳建完：

1. **Registry**：继续补充采集、分区、存储、质量策略；
2. **Collection Job**：任务模型和首次/增量/修复计划；
3. **一个模拟采集器**：先不依赖外部账号；
4. **Staging 与标准化**：保存采集结果并对齐类型；
5. **Validation**：Schema、主键、空值和覆盖检查；
6. **Storage Writer**：先实现一种简单 Parquet 策略；
7. **Catalog 与原子发布**：登记分区、文件和质量结果；
8. **SDK 读取**：按数据集和时间范围读取已发布数据；
9. **真实采集器**：TuShare、L2 文件/百度网盘等；
10. **概览与覆盖热力图**。

第一个完整样例可以选用：

```text
tb_l2.cn.stock.l2_order.sh
```

但如果真实 L2 文件格式尚不稳定，应先使用模拟采集器跑通闭环，再接入真实数据。

## 20. 后续 Agent 开发约束

后续 Agent 在修改项目前应遵守：

1. 不要擅自引入跨供应商统一业务 Schema；
2. 不要把淘宝或百度网盘直接当成供应商身份；
3. 不要把真实数据文件或密钥提交到 Git；
4. 不要让采集器直接写正式数据目录；
5. 不要通过扫描文件夹代替 Catalog；
6. 不要把逻辑分区和物理文件视为同一个概念；
7. 不要在 SDK 内隐式拼接数据集；
8. 不要将周末当作 A 股交易日；
9. 数据集 ID 和已启用 Schema 的变化必须可追踪；
10. 新功能应包含与风险相匹配的测试，并更新相关中文文档；
11. 提交前运行后端测试、Ruff 和前端构建；
12. 保持提交范围清晰，不混入无关改动。
